# Traceability Guide

The Azure Architecture Factory tracks requirements from BRD intake through to generated code, tests, and Bicep infrastructure. This guide explains how traceability works at each stage — from automatic matrix generation to deep coverage analysis with the `project-traceability-advisor` agent.

---

## Overview

| Stage | What is produced | When it happens |
|---|---|---|
| **BRD submission** | `docs/traceability-matrix.md` with REQ-NNN IDs, artifact mappings, and a coverage summary | Automatically on every project generation |
| **Traceability advisor** | `docs/traceability-report-<date>.md` with requirement → code → test → Bicep mappings and gap analysis | On demand via the **🔗 Traceability** button or direct Copilot prompt |
| **Manifest update** | `project-manifest.json` updated with a `traceability` block (coverage %, priority gaps) | Run by the advisor with `Update manifest: true` |

---

## Stage 1 — The Generated Traceability Matrix

Every project generated by the factory includes `docs/traceability-matrix.md`. It is created automatically from the BRD and contains:

### Requirement IDs

Each requirement extracted from the BRD is assigned a stable identifier:

```
REQ-001, REQ-002, ... REQ-NNN   ← functional, security, operational requirements
SC-001, SC-002, ...              ← success criteria
```

IDs are preserved across re-runs so reports are comparable over time.

### Artifact Mapping

Each requirement is mapped to the most likely generated artifact based on keyword analysis:

| Requirement signal | Mapped artifact |
|---|---|
| `api`, `endpoint`, `rest`, `integration` | Starter API — `src/copilot_api/main.py` |
| `auth`, `identity`, `rbac`, `secret`, `key vault` | Bicep infra — `infra/main.bicep` (Identity & RBAC) |
| `monitor`, `alert`, `log`, `metric`, `telemetry` | Architecture overview — `docs/architecture-overview.md` |
| `deploy`, `pipeline`, `ci`, `cd`, `container` | Deployment guide — `docs/deploy.md` |
| `govern`, `policy`, `compliance`, `audit` | Governance model — `docs/governance-model.md` |
| `test`, `validat`, `verif`, `acceptance` | Test scaffold — `tests/test_generated_project.py` |

### Status Column

| Status | Meaning |
|---|---|
| `Scaffolded` | The starter skeleton covers this requirement. Likely needs workload-specific refinement |
| `Pending Extension` | The requirement involves data stores, ML, workflows, or external systems — needs custom implementation |
| `Review Required` | Governance, compliance, or security requirement — needs architect or domain owner sign-off |

### Coverage Summary

At the bottom of every matrix:

```
| Status            | Count | Share |
|-------------------|-------|-------|
| ✅ Scaffolded      |   8   |  67%  |
| 🔧 Pending Ext.   |   3   |  25%  |
| 🔍 Review Reqd    |   1   |   8%  |
```

## Stage 2 — The Traceability Advisor (Deep Analysis)

The `project-traceability-advisor` agent goes further than the auto-generated matrix. It reads the actual generated files and maps every requirement to the specific code, tests, and Bicep resources that implement it.

### How to Invoke

**From the portal card:**
1. Find your project in the **Projects** list
2. Click **🔗 Traceability** — a toast confirms the prompt was copied
3. Open **VS Code Copilot Chat** (`Ctrl+Alt+I`)
4. Paste the prompt and press Enter

**Directly in Copilot Chat:**
```
Use project-traceability-advisor.
Project path: projects/my-project
Update manifest: true
```

### What the Advisor Examines

For each `REQ-NNN`, the advisor checks:

| Dimension | What it looks for |
|---|---|
| **Code coverage** | Which source files and functions address this requirement |
| **Test coverage** | Which test assertions validate this requirement |
| **Infrastructure coverage** | Which Bicep resources implement security, identity, or data requirements |
| **Documentation coverage** | Which doc references or describes this requirement |

### Implementation Status per Requirement

| Status | Meaning |
|---|---|
| `Implemented` | Code + at least one test + infra (if applicable) |
| `Partial` | Code exists but no test, or an infra gap was identified |
| `Scaffolded` | Only the generated starter logic; no workload-specific refinement yet |
| `Gap` | No artifact found — nothing implements this requirement |

## Understanding the Traceability Report

The report (`docs/traceability-report-<date>.md`) contains four sections:

### Executive Summary

```
Total requirements tracked: 12
Implementation coverage: 58% (Implemented: 7, Partial: 3, Gap: 2)
Test coverage: 42%
Infrastructure coverage: 67%
```

### Requirement Coverage Matrix

```
| ID      | Requirement                    | Type        | Source File(s)         | Test(s)               | Bicep Resource | Status    |
|---------|--------------------------------|-------------|------------------------|-----------------------|----------------|-----------|
| REQ-001 | Secure MCP aggregation         | Security    | src/.../copilot_svc.py | —                     | main.bicep     | Partial   |
| REQ-002 | REST endpoint for CSAs         | Functional  | src/.../main.py        | test_generated_proj.  | —              | Partial   |
| REQ-003 | Governance review checkpoint   | Governance  | —                      | —                     | —              | Gap       |
```

### Priority Gaps

Gaps are ranked by impact:

```
🔴 Critical (Security / Compliance)
   REQ-001 — No Bicep managed identity resource found

🟠 High (Functional — No Implementation)
   REQ-003 — No matching source code found

🟡 Medium (Tests Missing)
   REQ-002 — Code found in src/.../main.py but no test assertion
```

### Action Plan

```
1. [ ] Add Bicep managed identity module for REQ-001
2. [ ] Implement governance checkpoint logic for REQ-003 in src/.../
3. [ ] Add test_copilot_endpoint() to tests/test_generated_project.py for REQ-002
```

## Manifest Tracking

When run with `Update manifest: true` (the default via the portal button), the advisor adds a `traceability` block to `project-manifest.json`:

```json
{
  "traceability": {
    "reportDate": "2026-04-14",
    "reportPath": "projects/my-project/docs/traceability-report-2026-04-14.md",
    "totalRequirements": 12,
    "implemented": 7,
    "partial": 3,
    "gap": 2,
    "testCoverage": "42%",
    "infraCoverage": "67%",
    "priorityGaps": ["REQ-001 (no Bicep identity)", "REQ-003 (no code)"]
  }
}
```

Re-running the advisor after closing gaps updates this block, creating a coverage trend over time.

---

## Re-Running to Track Progress

The advisor is designed to be run repeatedly. Each run saves a new dated report:

```
docs/traceability-matrix.md             ← auto-generated at BRD intake (always overwritten)
docs/traceability-report-2026-04-10.md  ← first deep analysis
docs/traceability-report-2026-04-14.md  ← re-run after fixes
```

The coverage trend section in the report compares the current run to the previous baseline.

## Frequently Asked Questions

**Q: The matrix shows "Scaffolded" for everything. Is that a problem?**  
A: No — it means the starter skeleton covers the shape of each requirement but the workload-specific logic has not been added yet. Use the Action Plan from a full advisor run to prioritise what to build next.

**Q: A requirement has no matching artifact — what do I do?**  
A: That is a `Gap`. The advisor flags it as 🟠 High priority if it is functional, or 🔴 Critical if it is a security or compliance requirement. Assign it to a developer or architect with the action item from the report.

**Q: Can I add my own requirements that were not in the BRD?**  
A: Yes — add them as bullet points under a `## Requirements` section in `docs/architecture-overview.md`. The advisor reads this file as a fallback and will assign new REQ-IDs on the next run.

**Q: How often should I run the traceability advisor?**  
A: At minimum after each implementation sprint, before a production deployment, and before a stakeholder review. The dated reports give you an auditable coverage history.
