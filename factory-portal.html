Architecture Factory

End-to-end orchestration: Business Requirements → Architecture Design → Implementation → Testing → Deployment

What is the Azure Architecture Factory? A GitHub Copilot–powered workspace: Business Requirements → Architecture → Code → Bicep → Azure. ▸

Core Capabilities

  • BRD Intake — Submit a Business Requirements Document via the portal form; the factory pipeline starts automatically
  • Architecture Diagram — Generates an Azure draw.io diagram and companion notes from requirements
  • Code Scaffolding — Produces modular Python microservice source trees mapped to diagram components
  • Bicep Infrastructure — Creates parameterized Bicep modules for every Azure resource in the architecture
  • Infrastructure Validation — Auto-validates and self-heals Bicep syntax, logic, and module references before deployment
  • Production Readiness Review — Checklist of runtime, identity, secret, networking, and observability prerequisites
  • Optional Azure Deployment — Deploys the generated project to Azure via azd up or Bicep CLI
  • Project Registry — All outputs are isolated under projects/<slug>/ and indexed for future reference

Additional Features

  • Legacy App Modernization — Point the agent at an existing codebase; it assesses the stack, maps components to Azure services, generates a BRD, and runs the full factory pipeline automatically
  • Monorepo Support — Detects multi-service projects and produces a separate Azure target mapping per service
  • Assessment-Only Mode — Run the modernization assessment and produce the BRD without triggering the full factory; review before committing
  • Design Analysis — Analyze an existing architecture diagram against Azure best practices and Well-Architected Framework pillars
  • CSA Support Copilot — Ask operational and technical CSA questions through the hosted MCP companion service
  • Portal Documentation — Quick access to Quick Start, Getting Started, and the App Modernization Guide from the portal header

Factory Pipeline at a Glance

  1. Submit BRD → brd-to-architecture-diagram
  2. Diagram → azure-architecture-implementer
  3. Infrastructure → bicep-infrastructure-validator
  4. Readiness → production-environment-advisor
  5. Deploy → azure-project-deployer (optional)

Design Analysis & Rationale

Understanding the architectural patterns and design decisions

Factory Design Philosophy

The Azure Architecture Factory prioritizes production-readiness over simplicity. Each project uses cloud-native patterns that align with real enterprise workloads, including service isolation, asynchronous processing, audit trails, and observability built-in from the start.

▸ 🔄 Modernize a Legacy Application Point the agent at an existing codebase — it will assess, map to Azure services, generate a BRD, and run the full factory pipeline.

The modernization-to-factory agent inspects your legacy codebase, detects the technology stack and architecture pattern, maps each component to an Azure target service, writes a modernization assessment, generates a target-state BRD, and hands it to the factory pipeline — all automatically. The only required input is the path to the existing code.

1. Architectural Pattern Selection

Projects in the factory use microservices or domain-driven service boundaries depending on workload characteristics.

Pattern Best For Tradeoffs
Microservices (Container Apps) Stateless, event-driven workloads; independent scaling ✓ Fine-grained scaling
✗ Operational complexity
Kubernetes (AKS) Large, complex multi-service systems; cost-sensitive ✓ Dense packing
✗ Steep learning curve
Serverless Functions Short-lived, event-driven jobs; pay-per-execution ✓ Zero idle cost
✗ Cold starts
Monolith (App Service) Simple CRUD applications, small teams ✓ Simpler to reason about
✗ Harder scaling

2. Data Layer & Persistence Strategy

Each project selects datastores based on access patterns, consistency requirements, and scale characteristics.

Datastore Why Selected Alternative
Cosmos DB (NoSQL) Document flexibility, multi-region replication, high throughput PostgreSQL (operational overhead)
SQL Database Relational integrity, ACID guarantees, familiar schema Cosmos DB (overkill)
Blob Storage Immutable archive, massive scale, cost-effective Cosmos DB (wrong pattern)
Azure Search Full-text search, semantic ranking for LLM responses PostgreSQL fulltext (less performant)

2A. Project-by-Project Analysis Groups

Use View Analysis from each project card to jump to the right group below.

Ticket Triage Assistant
Design Choice

Container Apps microservices with Service Bus and Cosmos DB for independent scaling and durable approval workflows.

Benefits

Fault isolation, stronger auditability, and better handling of bursty ticket volumes.

Alternative Considered

A single monolith was simpler but rejected due to scaling bottlenecks and weaker service isolation.

Order Management Platform
Design Choice

Event-driven functions with Service Bus, SQL, and Storage to process order lifecycle steps asynchronously.

Benefits

Lower cost under variable demand, durable retries, and stronger consistency for transactional data.

Alternative Considered

Pure synchronous APIs were rejected because downstream failures can block the full checkout flow.

AKS Microservices Demo
Design Choice

AKS and Helm for teams that require Kubernetes-native control and denser multi-service placement.

Benefits

Advanced scheduling control, ecosystem compatibility, and platform-team governance flexibility.

Alternative Considered

Container Apps was easier operationally but offers less cluster-level control for advanced requirements.

E-Commerce Demo
Design Choice

App Service and Static Web Apps with Cosmos DB and Search to maximize development velocity.

Benefits

Simpler operations, fast delivery, and strong product discovery UX through search capabilities.

Alternative Considered

Full microservice decomposition was deferred to avoid unnecessary complexity early in product validation.

Storage Self-Service Provisioning
Design Choice

Functions with Event Grid and Key Vault for policy-driven provisioning with secure secret handling.

Benefits

Strong governance automation, event decoupling, and clearer compliance checkpoints.

Alternative Considered

Manual request handling was rejected due to inconsistent operations and weak end-to-end traceability.

Fabric Medallion Pipeline
Design Choice

Medallion zones on Fabric with Spark and Lakehouses to separate raw, curated, and serving layers.

Benefits

Better data quality progression, stronger lineage, and repeatable transformations at scale.

Alternative Considered

Single-zone pipelines were rejected because quality issues propagate and are harder to contain.

BRD-Based Project Template
Design Choice

Template-first project scaffolding with placeholders for architecture, infra, docs, and tests.

Benefits

Consistent project structure, faster onboarding, and easier governance across generated outputs.

Alternative Considered

Free-form initialization was rejected because outputs become inconsistent and difficult to review.

3A. Model Selection Rationale by Project

Each AI-enabled project selected models based on quality, latency, cost, and safety. Here's the reasoning:

Ticket Triage Assistant: GPT-4o for Classification + Drafting
Why GPT-4o

Chosen Model: GPT-4o for ticket analysis and draft response generation.
Reasoning: Ticket triage requires understanding nuanced customer intent, multi-step reasoning (classify → route → draft response), and high-quality outputs that humans will review. GPT-4o excels at complex reasoning and produces more accurate, safer responses.

Alternatives Considered

GPT-3.5 Turbo: Faster and cheaper, but produces lower-quality drafts that require more human editing. Cost savings don't justify the review overhead in production.
Phi-3.5 (local): Free and private, but insufficient reasoning ability for nuanced customer interactions and compliance requirements.

Embeddings Layer

text-embedding-3-large is used for semantic search to retrieve similar past tickets. These embeddings feed into RAG (Retrieval-Augmented Generation) so the model can cite historical resolutions, making responses more trustworthy and reducing hallucinations.

Order Management Platform: GPT-3.5 Turbo for Routing
Why GPT-3.5 Turbo

Chosen Model: GPT-3.5 Turbo for order-to-fulfillment routing and state classification.
Reasoning: Order routing is simpler than ticket triage-mostly classification ("is this eligible for express shipping?") and straightforward text processing. GPT-3.5 Turbo processes these tasks accurately and costs ~10x less than GPT-4o. The speed is also acceptable for async processing pipelines.

Alternatives Considered

GPT-4o: Overkill for classification; wastes budget on unnecessary reasoning capability.
Phi-3.5 (local): Could work but would require fine-tuning on order data; higher operational burden for marginal cost savings.

Cost Impact

At 1000 orders/day, GPT-3.5 Turbo costs ~$10/month vs. GPT-4o at ~$100/month. With async processing, latency is not a factor.

E-Commerce Demo: GPT-4 Turbo for Product Descriptions
Why GPT-4 Turbo

Chosen Model: GPT-4 Turbo for generating rich, SEO-friendly product descriptions from structured catalog data.
Reasoning: E-commerce product quality directly impacts conversion. GPT-4 Turbo offers better tone consistency, product knowledge, and can handle 128K context (entire product catalog in one prompt). Quality matters more than cost here.

Alternatives Considered

GPT-4o: Newer and slightly better, but 128K context in Turbo is sufficient and slightly cheaper.
GPT-3.5 Turbo: Produces generic, lower-quality descriptions that don't drive conversions.

Safety & Brand Risk

Poor product descriptions can damage brand perception and lost sales revenue far exceeds the model cost. GPT-4 Turbo strikes the right balance between quality and cost.

4. Key Benefits of Factory Designs

Production-Ready from Day 1

Every project includes observability (App Insights), error handling, RBAC with managed identity, and deployment automation.

Decoupled Scaling

Microservices and async messaging allow each component to scale independently without affecting others.

Audit & Compliance Built-In

Service Bus message capture, Cosmos DB change feeds, and audit logs ensure you can trace every state change.

Testable Architecture

Service boundaries enable unit and integration tests without end-to-end UI testing. Mock queues and storage for fast feedback.

Cost Optimization

Serverless components scale to zero. Cosmos DB uses pay-per-request mode. Container Apps uses per-vCore per-second billing.

Modular IaC

Bicep modules are reusable across projects. Update security policies in one place; all projects inherit the change.

5. When NOT to Use Factory Patterns

  • Simple CRUD apps with <10 QPS: Factory's microservice patterns add unnecessary overhead. Use a single App Service instead.
  • Real-time complex queries: Cosmos DB NoSQL is not a good fit for ad hoc analytics. Use SQL Database or Synapse Analytics.
  • Long-running batch jobs (>60 minutes): Azure Functions have timeout limits. Use Data Factory or Spark on Databricks.
  • Synchronous request-response at scale: Service Bus queues add latency. For low-latency RPC, use direct HTTP/gRPC.
