# Factory Template: Microsoft Agent Framework SDK Runtime

This folder is a **reusable factory template**. Projects generated by the Azure
Architecture Factory that need LLM-driven agents can adopt this runtime pattern
by copying the files in this folder and following
[`docs/AGENT_FRAMEWORK_RUNTIME_PATTERN.md`](../../docs/AGENT_FRAMEWORK_RUNTIME_PATTERN.md).

## When to use

Adopt this template when a generated project:

- Has one or more LLM-driven agents (extraction, chat, orchestration, clarification).
- Needs **function-calling** so the LLM can call typed Python tools instead of the
  project parsing free-form text with regex.
- Needs managed-identity authentication to Azure AI Foundry (no API keys).
- Wants to keep a deterministic fallback runtime so the service stays online when
  the SDK is missing or the Foundry endpoint is unreachable.

Do **not** adopt this template for projects that have no LLM component — the
deterministic Python services remain the right choice there.

## What's in here

| File | Purpose |
|------|---------|
| [`install_agent_framework.ps1`](install_agent_framework.ps1) | Two-phase pip install (Windows) that gets `agent-framework-*` rc6 past the `azure-ai-agentserver-*` rc3 pin |
| [`install_agent_framework.sh`](install_agent_framework.sh) | Linux / CI equivalent of the PowerShell installer |
| [`requirements.agent-framework.txt`](requirements.agent-framework.txt) | Canonical pin list for the preview SDK (commented; not auto-installed) |
| [`foundry_agent_runtime.template.py`](foundry_agent_runtime.template.py) | Annotated reference adapter showing how to wrap `FoundryChatClient` + `Agent` around the project's existing deterministic services |

## How projects adopt it

1. Copy `install_agent_framework.ps1` and `install_agent_framework.sh` into the
   project's `scripts/` folder.
2. Copy `foundry_agent_runtime.template.py` into `src/<package>/services/` and
   rename to `foundry_agent_runtime.py`. Wire its tool callables to the
   project's own QA / repository / clarification helpers.
3. Add the four env flags (`AGENT_FRAMEWORK_ENABLED`,
   `FOUNDRY_PROJECT_ENDPOINT`, `FOUNDRY_MODEL_DEPLOYMENT_NAME`, and a
   derived `foundry_runtime_enabled` property) to the project's `Settings`
   dataclass.
4. Gate the runtime selection in the project's agent-runtime factory:
   prefer `build_foundry_runtime(...)` when `foundry_runtime_enabled` is
   true, and fall back to the deterministic local runtime on `ImportError`
   or missing configuration.
5. Copy the commented pins from `requirements.agent-framework.txt` into the
   project's `requirements.txt` (kept commented — the installer scripts own
   the actual install order).
6. Update the project's `README.md` and `DEPLOY.md` to point at the new
   installer scripts and env flags.

The files in this folder are the authoritative reference. They are
designed to be self-sufficient — an adopter should be able to follow
this README without reading any other project's source.

## The deterministic-contract pattern

Every tool the SDK `Agent` calls **must** delegate mutation to a pure
Python helper that already exists in the project (e.g. a
`apply_answer_to_domain_object` merge helper). The LLM decides *which*
tool to invoke; the helper decides *how* the underlying state changes.
This keeps schema validation, audit logging, and persistence identical
across both runtimes and makes the SDK runtime strictly additive.

See the pattern doc for the full rules and the forward-progress safety
net that guarantees multi-turn loops always advance even when the LLM
returns without calling a tool.
